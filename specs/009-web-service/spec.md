## Clarifications

### Session 2026-10-19

本节开工前（H0 依赖核对阶段）有四处冲突/抉择触发了软门禁，已全部报用户裁决。四条裁决是后续 plan / tasks / 实现的硬约束。

- Q: 错误响应的信封用哪个字段名？**这是一处课件自相矛盾**——课件正文 §三.3 明写「复用既有 `ApiResponse`（`code`/`message`/`data`/`timestamp`）」，但同一节验收 harness 的示例测试断言的是 `$.errorCode` = `"INTERNAL_ERROR"`。本仓已入库的契约 `specs/000-runtime-kernel/contracts/rest-api.md`（骨架期定稿、10 个端点逐条写明）与技术方案 §7.1 都只有 `code`（值 = HTTP 状态码），既有 `ApiResponse` 类也是这个形状。 → A: **沿用 `{code, message, data, timestamp}`，不引入 `errorCode`**。判据：① 契约是骨架期定稿并逐条写明 10 个端点的既有事实，改它要回修前序节契约文档；② 课件正文自己就说「复用既有 `ApiResponse`」；③ 课件的意图（500 响应体不泄漏内部异常描述）与字段名无关，可完整保住。**连带**：课件 harness 那条断言译成「`code` = 500 + `message` 为统一话术 + 响应体不含内部异常 message」，断言逻辑逐条保真。

- Q: 「Agent 调用最长 60 秒超时返回 504」怎么落地？技术方案 §7.4 明写要它，但 H4 全局不变量 ⑤ 是硬门禁：「全程同步阻塞——出现 Reactor / `CompletableFuture` / 自建线程池即违规」。**同步模型下没有不引入第二个线程就能掐断一个阻塞调用的办法**，两者直接对撞。 → A: **只落异常类型与 504 映射，不做强制掐断**。判据：① H4 ⑤ 是硬门禁，撞它即未完成；② 课件 harness 判卷的是「每类异常映射到约定状态码」，不要求超时机制本身；③ 与第 25 节「Step 3 那行 WARN 结构上不可达、如实记为已知边界」同口径。**连带**：课件「做完怎么验」里「构造超 60 秒调用拿 504」这条人工项**本节不可达**，验收报告 MUST 如实记为已知边界，MUST NOT 假装验过。

- Q: 第 18 节遗留的 `OryxosApplication`（`oryxos-boot` 的启动类）怎么处理？`specs/003-cli-session/` 明写「去留由第 26 节定」，并留下了一笔账：它自己的 `scanBasePackages = "io.oryxlabs.oryxos"` 是宽根，与 `CliApplication` 反向撞车（`BeanDefinitionOverrideException`）处于潜伏期；而本节 `serve` 要真起 servlet 容器。 → A: **删除该类**。判据：① fat JAR 主类自第 18 节起就是 `OryxOsCli`，它无 `main` 调用方；② `oryxos-boot` 无 `src/test`，删除不牵动测试；③ 删掉即永久消除潜伏的反向撞车，比「收窄扫描根」少一个将来仍需解释其分工的启动类。**连带**：`CLAUDE.md` 里对它「不再是主类、去留由第 26 节定」的表述须一并回修。

- Q: `IllegalStateException` 映射成哪个状态码？课件把 `IllegalStateException` 整个映射成 503（Provider 故障）；但本仓 `AgentService.process` 用 `IllegalStateException` 表示「会话所属 Agent 的 Profile 不存在」——那是 404 语义。照课件写，运维配错 Agent 名会拿到 503 并去查 Provider，而契约 `rest-api.md` 明写「资源不存在(session / agent) → 404」。 → A: **按领域异常精确映射，不 blanket 映射**。判据：① 契约已定 404 口径，blanket 503 与它冲突；② 503 的语义是「Provider 故障」，被误用的代价是排障方向被带偏（与第 25 节时区坑同一类：**看起来成功的错误**）。**连带**：Provider 故障由 `oryxos-provider` 的专用异常映射 503，本仓现有 `ProviderNotFoundException` 的语义是「厂商名不在显式映射表里」＝配置错误，归 500，MUST NOT 混进 503。

- Q: `GET /api/v1/health` 里「各 Provider 的连通状态」怎么得出？契约 `rest-api.md` 写的字面是「任一 Provider **不可达**不拉低总状态（只如实报告）」，而真实探测意味着每次健康检查都发一次模型调用——健康检查是运维**高频轮询**的端点，把外部依赖的可用性绑到它身上，会让外部抽风变成我们自己健康状态横跳，且轮询频率越高花得越多。 → A: **只报「配置就绪」，不发真实请求**。判据：① 健康检查 MUST 廉价且稳定，不依赖外部服务的瞬时可用性；② 凭证在场 + 厂商在映射表里，正是运维真正能自己动手修的那两件事——报它才可行动；③ 与第 25 节同一条口径：**如实**比**好听**重要。**连带**：响应字段的措辞 MUST 跟着改（用「就绪 / 未就绪」，MUST NOT 用「连通 / 不可达」——那是我们没测过的事）；这是对已入库契约 `rest-api.md` 里「不可达」二字的**语义收窄**，须在该契约挂带日期修订注。

## 范围说明

Provider、ReAct、CLI、Notify、Tool、Memory、Sandbox、Scheduler 都已交付——Agent 能被喂话、会想、会动手、会往外推消息、记得住事、干活有安全边界、还能到点自己跑。但**这些能力只有 CLI 一个对外出口**，业务系统用不上。本节补的是**能力五：Web Service**——把底座已有的能力包装成 REST API，让任何能发 HTTP 请求的语言都能接进来（核心阶段不出 SDK）。

**一句话定位：Web Service 是 OryxOS 的对外门面。** 没有它，OryxOS 只是一个 CLI 工具；有了它，它才是一个能被业务系统集成的底座。这也是它区别于偏个人定位工具的关键能力。

**Controller 必须薄，跟 CLI 是同一个引擎。** CLI 是「读—转交—打印的壳」，HTTP 处理层是一模一样的角色：参数校验、响应包装、错误处理，三件事之外一概不碰。发消息端点进来后调的还是那个 `AgentService.process`——跟 `oryxos chat` 走的是**同一个方法**。这是章程原则 IX（三种触发源汇入同一入口）的第四次兑现，也是最容易被「顺手在 Controller 里加点逻辑」破坏掉的一条。

**异常出口只有一个。** 六个 Controller 都不自己拼错误响应，所有异常统一交给一个异常出口转成标准 JSON。这个口径一开始就定死，业务系统对接时才不用逐个端点猜错误格式。

**管理台是第二个交付物，且它没有自己的后端。** 所有数据都来自这同一批端点——这也顺带验证了「API 是完备的对外通道」这件事本身。这一版**只读**。

**本节交付物范围**（课件「本节交付物」逐项）：

- **代码**：六个 Controller（Session / Agent / Profile / Memory / Tool / System）、统一异常出口（**扩展既有、复用既有信封**）
- **测试**：`SessionApiControllerTest`、`GlobalExceptionHandlerTest`、`WebSmokeIT`（见验收 harness）
- **配置**：虚拟线程开启、端口 8080、消息 32KB 上限 / 历史 100 条上限；常驻模式只靠一个 Provider 凭证就起得来
- **前端**：`oryxos-web/src/main/frontend/` 下由提示词生成的 Vue 3 + Vite 只读管理台（五页调五个查询端点），构建产物落到 `static/admin/`、由服务端托在 `/admin`；构建串联方式（构建期绑定 / 手动构建）plan 里二选一；SPA 路径回落 `/admin/**` → `index.html`
- **风格 skill**：`.claude/skills/oryxos-admin-ui/SKILL.md`（固化官网首页设计 token + 工程约定 + 组件 / 三态规范 + 验收清单）——生成管理台就调它，30 节加 Agent 管理页复用同一套
- **模块落位**：Controller / 异常处理 / static-admin → `oryxos-web`（技术方案 §7.1）

**四个「想清楚」（课件「动手前先想清楚」逐项）**：① Controller 薄、跟 CLI 共享引擎；② 异常单出口、错误码定死；③ 不做认证 / 流式 / 限流 / RBAC，但要有 32KB 与 100 条两条防呆限制；④ 常驻模式必须只靠一个 Provider key 就起得来（框架的急切自动装配会额外索要第二个 key，必须排掉）。

### 明确不做（边界）

课件「有几样先别做」逐项照搬：

- **认证机制**——假设内网部署，扩展阶段补 API Key + JWT
- **流式响应（SSE）、WebSocket**——核心阶段同步阻塞模型
- **限流、RBAC 权限**
- **Profile 的增删改端点、长期记忆的写入端点、「通过 API 定义一个 Agent」**（Agent 目录的上传 / 查看 / 更新 / 删除）——归 29 / 30 节，本节刻意留白；**界面上也不该出现假按钮**
- **Webhook 触发、Prometheus metrics 端点**
- **核心阶段不出 SDK**——跨语言集成靠「任何能发 HTTP 请求的语言」这条通用性

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 业务系统通过 HTTP 与 Agent 连续对话 (Priority: P1)

业务系统要跟某个 Agent 保持一段连续对话：先创建一个会话，然后反复往这个会话发消息，每次同步拿到 Agent 的最终答复；隔天回来还能查到完整历史；谈完了把它归档。

**Why this priority**: 这是 Web Service 存在的**首要理由**——没有它，业务系统无法把 Agent 接进自己的流程，OryxOS 就只是一个 CLI 工具。会话管理的四个端点加上统一信封与统一异常出口，构成对外门面的最小可用闭环；它也是唯一能证明「HTTP 层与 CLI 共享同一个引擎」这条架构约束的切片。

**Independent Test**: 只实现会话管理的四个端点 + 统一信封与异常出口，即可用 HTTP 客户端完成「建会话 → 发消息 → 查历史 → 归档」全流程并验证全部错误码映射；不需要管理台、不需要其余六个端点。

**Acceptance Scenarios**:

1. **Given** 工作区里存在一个可用的 Agent，**When** 业务系统创建会话并向它发一条消息，**Then** 同步拿到该 Agent 的最终答复，且响应体是统一信封（`code` = 200）。
2. **Given** 一个已存在的会话，**When** 业务系统再发一条消息，**Then** Agent 能看到这个会话此前的历史（多轮对话成立）。
3. **Given** 一条超过 32KB 的消息，**When** 业务系统把它发给某个会话，**Then** 拿到 400，且**没有任何一次模型调用或工具执行发生**。
4. **Given** 一个不存在的会话标识，**When** 业务系统向它发消息或查历史，**Then** 拿到 404，响应体仍是统一信封。
5. **Given** 会话所属 Agent 的配置已经不可用，**When** 业务系统发消息，**Then** 拿到 404（资源不存在），**不是** 503——排障方向必须指向「Agent 配置」而不是「Provider」。
6. **Given** Provider 侧不可达，**When** 业务系统发消息，**Then** 拿到 503。
7. **Given** 一个已归档的会话，**When** 业务系统再次归档它，**Then** 拿到与首次归档相同的结果（幂等）。
8. **Given** 一个内部错误（例如数据库连接失败），**When** 业务系统收到 500，**Then** 响应体里**不含**内部异常的描述（连接串、堆栈一类），完整信息只进日志。

### User Story 2 - 业务系统一次性调用某个 Agent (Priority: P2)

业务系统不想管会话，只想把一条消息发给某个 Agent、拿一次答复就走（适合 CI/CD、告警系统这类无状态短任务）。

**Why this priority**: 这是课件点名的「业务系统最常用的两条路」中的第二条。它独立于 US1 的会话管理（不需要先建会话），但复用同一套信封与异常出口，故排在 US1 之后。

**Independent Test**: 只实现这一个端点即可验证：同一个 Agent 连续调两次，两次之间不共享任何上下文；且该端点不创建持久会话。

**Acceptance Scenarios**:

1. **Given** 一个可用的 Agent，**When** 业务系统按 Agent 名发起一次无状态调用，**Then** 同步拿到答复，响应体含 Agent 名与答复文本。
2. **Given** 同一个 Agent，**When** 业务系统连续调用两次，**Then** 第二次**看不到**第一次的对话内容（每次调用独立）。
3. **Given** 一个不存在的 Agent 名，**When** 业务系统调用它，**Then** 拿到 404。

### User Story 3 - 运维不写代码就能看清底座现状 (Priority: P3)

运维 / 业务方想回答四个问题：有哪些 Agent（各自能不能用）？注册了哪些工具？长期记忆里记了什么？Provider 通不通、底座跑了多久？——通过查询端点拿到真实数据。

**Why this priority**: 这些是**只读**信息端点，不承载核心业务价值，但没有它们，前两个 US 的运维体验是黑的。它也是管理台（US4）唯一的数据来源，故先于 US4。

**Independent Test**: 只实现这五个查询端点即可验证：逐个请求并核对返回内容与工作区真实状态一致（Agent 数、工具数、记忆全文、Provider 状态、运行时长）。

**Acceptance Scenarios**:

1. **Given** 工作区里有若干 Agent，**When** 运维查询 Agent 列表，**Then** 返回全部 Agent 及其配置摘要，**且配置不可用的 Agent 也在列表里**（标注为无效并附原因），MUST NOT 静默隐藏。
2. **Given** 注册表里有内置 / 注解 / MCP 三类来源的工具，**When** 运维查询工具列表，**Then** 返回全部工具及其来源标注。
3. **Given** 长期记忆里有内容，**When** 运维查询记忆，**Then** 返回核心区全量与归档区内容，且**每次实时读**（改完立即生效，不缓存）。
4. **Given** 某个 Provider 的凭证环境变量未配置，**When** 运维查询系统状态，**Then** 该 Provider 被标为「未就绪」，**且不因此把整体状态拉低**；系统 MUST NOT 为了回答这个问题去发一次真实模型调用。
5. **Given** 服务正在运行，**When** 运维查询健康状态，**Then** 返回服务与数据库的状态。

---

### User Story 4 - 只读管理台 (Priority: P4)

运维打开浏览器访问服务同端口的 `/admin`，看到左侧五项导航（会话列表、Agent 列表、工具列表、长期记忆、运行状态），右侧渲染真实数据。

> 修订注（2026-10-19，实现后复核）：导航第一项在实现里叫**「会话」**，页面形态是**按会话 ID 查询**，不是「会话列表」——本节 10 个端点里**没有 `GET /api/v1/sessions`（列表）**，界面不能暗示一个不存在的功能。原文「会话列表」是需求期的措辞，保留以免抹掉当时的意图。
>
> 修订注（2026-10-20，第 27 节）：上一条已失效——第 27 节交付了 `GET /api/v1/sessions`（最近 100 条摘要，`?status=` 可选），管理台第 1 页改为「**列表 + 点一行看详情**」，导航仍七项、只读纪律不变。第 26 节的 10 个端点签名未动，端点总数现为 11。

**Why this priority**: 它是「API 是完备的对外通道」的**自证**——管理台没有自己的后端，五页数据全部来自 US1/US3 的端点。它纯消费既有端点，不新增对外契约，故排在最后；但它有独立可验收的判据（五页渲染真实数据、零写操作入口）。

**Independent Test**: 服务端起好后访问 `/admin`，五页各自渲染出与 US3 端点一致的**真实**数据；页面上找不到任何新建 / 编辑 / 删除控件；直接访问 `/admin` 下的子路径刷新不 404。

**Acceptance Scenarios**:

1. **Given** 服务已启动，**When** 运维访问 `/admin`，**Then** 看到五项导航与默认页内容，数据与对应查询端点一致。
2. **Given** 某个查询端点返回错误，**When** 管理台渲染该页，**Then** 把统一信封里的 `message` 显示出来（不是白屏、不是原始 JSON 堆）。
3. **Given** 数据为空（例如一个 Agent 都没有），**When** 管理台渲染，**Then** 显示明确的空态占位（不是白屏）。
4. **Given** 管理台的任一页面，**When** 通读全部控件，**Then** **零**个新建 / 编辑 / 删除入口。
5. **Given** 管理台内部有前端路由，**When** 运维在子路径上直接刷新浏览器，**Then** 页面正常加载（服务端回落），且 `/api/v1/**` 的响应不受回落影响。
6. **Given** 运维想自己调接口，**When** 访问交互式文档页，**Then** 能看到自动生成的、覆盖 10 个端点的接口文档。

### Edge Cases

- **消息超限**：> 32KB 的消息 MUST 在进入处理入口**之前**被拒（400），MUST NOT 先跑一遍模型再拒。
- **会话历史过长**：单个会话历史超过 100 条时，查询端点 MUST 只返回最近 100 条（MUST NOT 报错、MUST NOT 全量返回）。
- **配置不可用的 Agent**：MUST 出现在 Agent 列表里并标注原因，MUST NOT 静默隐藏（隐藏会让「Agent 配好了但没生效」变成看不见的软故障）。
- **只靠一个凭证启动**：常驻模式 MUST 只靠一个 Provider 凭证环境变量就起得来；框架层面的急切自动装配若额外索要第二个凭证，MUST 被排掉（否则运维要配两个 key，且「干净机器上快速部署」这条会卡死）。
- **Provider 故障**：MUST 返回 503，MUST NOT 让整个进程退出。
- **数据库不可达**：健康状态 MUST 如实反映（数据库不可达时整体状态降级），MUST NOT 谎报健康。
- **归档会话再发消息**：MUST 返回 400（参数错），MUST NOT 静默复活一个已归档会话。
- **管理台资源缺失**：构建产物不存在时 MUST 有明确表现，MUST NOT 让服务启动失败（服务端能力与前端产物解耦）。
- **重复归档**：幂等，重复归档返回相同结果。
- **并发请求**：同步阻塞模型 + 虚拟线程下，并发调用 MUST NOT 互相阻塞到不可用（课件人工项：200 并发压一把）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在 `serve` 模式下对外提供 HTTP 接口，统一前缀 `/api/v1`，按资源分六组共 **10** 个端点：会话管理 4 个（创建、发消息、查历史、归档）、Agent 无状态调用 1 个、信息查询 3 个（Agent 列表、长期记忆、工具列表）、系统状态 2 个（健康、信息）。**只有 `serve` 起 HTTP 服务**（技术方案 §8.6 的三种运行模式表：`gateway` 是守护进程挂多个入站通道，归扩展阶段）。
- **FR-002**: HTTP 处理层 MUST 只做参数校验、响应包装、错误处理三件事，实际逻辑 MUST 委托给核心层既有服务；发消息端点 MUST 汇入与 CLI **完全相同**的处理入口，MUST NOT 在 HTTP 层另起一条处理链路。
- **FR-003**: 所有异常 MUST 由一个统一出口转成标准 JSON，MUST NOT 由各端点自行拼错误响应。
- **FR-004**: 错误码 MUST 用标准 HTTP 语义：400 参数错误、404 资源不存在、500 内部错误、503 Provider 故障、504 Agent 调用超时。
- **FR-005**: 500 的响应体 MUST NOT 泄漏内部异常的描述（连接串、堆栈一类）；完整信息 MUST 只进日志。
- **FR-006**: 成功与错误 MUST 共用同一个响应信封 `{code, message, data, timestamp}`，`code` 的值 MUST 为 HTTP 状态码。
- **FR-007**: 「会话所属 Agent 不存在」MUST 映射为 404，MUST NOT 映射为 503。
- **FR-008**: 单条消息 MUST ≤ 32KB，超限 MUST 在进入处理入口前被拒（400）。
- **FR-009**: 会话历史查询 MUST 最多返回最近 100 条。
- **FR-010**: 常驻模式 MUST 只靠一个 Provider 凭证环境变量就起得来；框架层面的急切模型自动装配 MUST 被排除。
- **FR-011**: 系统 MUST 自动生成 OpenAPI 3.0 文档并暴露交互式文档页，MUST NOT 手写接口文档。
- **FR-012**: 系统 MUST 提供一个跑在同一端口 `/admin` 子路径下的只读管理台，五个页面（会话、Agent、工具、长期记忆、运行状态）分别调用上述查询端点渲染真实数据。
- **FR-013**: 管理台 MUST NOT 出现任何新建 / 编辑 / 删除入口。
- **FR-014**: 管理台 MUST 与项目官网首页共用同一套设计语言（深色底 + 橙色强调、同一套字体与状态色），且这套设计规范 MUST 固化成**项目内**可复用的 skill，供后续给管理台加页时调用。
  > **2026-10-20 修订（用户裁决）**：其中的「深色底 + 橙色强调」不再成立。管理台 MUST 与官网首页的**实际外观**一致——**默认浅色**（官网 `:root` 档），系统偏好深色时切到官网的深色档（与 VitePress 默认跟随系统相同），MUST NOT 固定深色。令牌仍逐字取自 `website/.vitepress/theme/custom.css`，浅深两档由 `AdminThemeSourceTest` 逐字判卷。
- **FR-015**: 管理台 MUST 具备加载中 / 空数据 / 错误三种明确占位状态，MUST NOT 白屏；错误态 MUST 显示统一信封里的 `message`。
- **FR-016**: 管理台为单页应用，服务端 MUST 对 `/admin/**` 的未命中路径回落到 `index.html`，且 MUST NOT 影响 `/api/v1/**`。
- **FR-017**: 请求 MUST 跑在虚拟线程上，全程同步阻塞，MUST NOT 引入响应式编程构件。
- **FR-018**: Agent 列表 MUST 包含配置不可用的 Agent（标注为无效并附原因），MUST NOT 静默隐藏。
- **FR-019**: 长期记忆查询 MUST 实时读取（不缓存），改完立即生效。
- **FR-020**: 系统状态端点 MUST 如实报告各 Provider 的**配置就绪状态**（该厂商在映射表里且凭证环境变量在场 = 就绪，否则未配置），MUST NOT 发真实请求去探测；未就绪的 Provider MUST NOT 拉低整体状态，但数据库不可达 MUST 拉低整体状态。响应里 MUST 用「就绪 / 未就绪」的字面语义，MUST NOT 用「连通 / 不可达」这类它没有实际测过的措辞（软门禁裁决 ⑤）。
- **FR-021**: 归档端点 MUST 幂等——重复归档同一个会话返回相同结果。
- **FR-022**: 被拒的请求（400 / 404）MUST NOT 触发任何一次模型调用或工具执行（审计表中零行）。
- **FR-023**: 跨源请求 MUST 在核心阶段全开放（方便调试）；扩展阶段才加来源白名单（技术方案 §7.4）。
- **FR-024**: `serve` MUST 支持显式指定监听端口（默认 8080），指定的端口 MUST 真的生效——MUST NOT 只把参数回显出来却仍监听默认端口（第 18 节交付的 `serve` 目前只回显，本节的「端口在第 26 节启用」这句到此兑现）。

### Key Entities

- **会话（Session）**：一段连续对话的载体。对外暴露标识、所属 Agent、接入渠道、用户标识、状态（活跃 / 已归档）、消息历史、三个时间戳。**本节只读 / 归档，不新建会话概念**——标识的生成规则与存储归前序节。
- **Agent 配置（Profile）**：一个 Agent 的运行时配置。对外暴露名称、描述、Provider（厂商 + 模型）、工具子集、定时规则、是否可用（含不可用原因）。
- **工具（Tool）**：底座能给 Agent 用的一个动作。对外暴露名称、描述、输入结构、来源（内置 / 注解 / MCP 三类）。
- **长期记忆（Memory）**：Agent 的跨会话成长记录。对外暴露核心区全量与归档区内容。
- **响应信封（Envelope）**：成功与错误共用的统一外壳。含状态码、消息、数据、时间戳。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 业务系统**不改 OryxOS 一行代码**，仅凭接口文档即可完成「创建会话 → 发消息 → 查历史 → 归档」全流程。
- **SC-002**: 10 个端点全部可达，且**任一**端点的错误响应都符合同一份信封与状态码约定（一致性 100%，无例外）。
- **SC-003**: 非法输入（消息超限、会话不存在、Agent 不存在）100% 被拒，且**零次**模型调用与工具执行发生（可用审计表核对）。
- **SC-004**: 常驻模式在**只有一个** Provider 凭证环境变量的机器上启动成功，额外凭证需求为 **0**。
- **SC-005**: 运维无需任何命令行工具，仅凭浏览器即可查看五类运行信息，且五页数据与对应端点返回值**逐项一致**。
- **SC-006**: 管理台页面上可写操作入口数量为 **0**。
- **SC-007**: 单条消息超过 32KB 时被拒的时间**不随消息体积增长**（在进入处理入口前就拒，不跑模型）。
- **SC-008**: 200 并发调用下服务不降级（请求全部得到响应，无超时失败）。
- **SC-009**: 从「以另一个入口（CLI）聊过一轮」到「从查询端点读到该会话」，无需任何额外操作——两个人推入口共享同一份存储。
- **SC-010**: 连续查询系统状态 **100** 次，产生的对外模型调用数为 **0**（健康状态必须廉价且不依赖外部服务的瞬时可用性）。

## Assumptions

- **目标用户**：企业内网部署的运维方与业务系统开发者；假设内网可信，故核心阶段不做认证。
- **部署形态**：单实例、单二进制部署；常驻进程由运维自行拉起。
- **凭证来源**：Provider 凭证走环境变量注入，不落明文（沿用前序节既定口径）。
- **构建产物**：管理台的前端源码随仓库跟踪，构建产物由构建流程产出；产物缺失时服务端能力不受影响。
- **依赖**：依赖前序各节交付的核心层服务——Provider（能力一）、统一处理入口（能力二）、会话持久化（第 18 节）、Profile 注册表（第 16 节）、工具注册表（第 20 节）、长期记忆门面（第 22 节）。
- **不新增第三方依赖**：HTTP 层与接口文档能力由既有依赖提供（技术方案 §7.1 已列入模块组成）。
- **超时语义**：60 秒超时的**强制掐断**机制核心阶段不做（撞「全程同步阻塞」硬门禁），只保留异常类型与 504 映射；对应的人工验收项记为已知边界，MUST NOT 假装验过。
