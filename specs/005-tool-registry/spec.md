## 范围说明

前 19 节把 Agent 的"脑子"和"嘴"都装好了：第 16 节让它会调模型，第 17 节让它会想（ReAct 循环），第 18 节让它能一问一答，第 19 节让它能把结果主动推出去。**但它至今只会"想"和"说"。** 大模型本身只会生成文字——它读不了磁盘上的文件，也发不出一个 HTTP 请求。本节补的是让 Agent 真正能干事的那双手：**LLM 决定"调哪个工具、传什么参数"（第 16 节的 Function Calling），OryxOS 负责把这个工具真正执行掉、再把结果递回给 LLM。** 这正是 ReAct 循环里 "Act" 那一步。

本节同时是「统一抽象」这个设计习惯在本课最大的一次兑现：工具的来源五花八门——底座自带的、业务方用 Java 写的、通过外部服务接进来的——如果循环要分来源区别对待，代码会很快乱掉。本节把它们全部收敛到同一个抽象下，**ReAct 循环完全不感知工具从哪来**。

本节也是前 19 节埋下的三处伏笔的**集中兑现点**：第 17 节交付的工具执行器与 `tool_invocations` 审计表、第 17 节在 core 留下的「按名查工具 / 列可用工具」接缝、第 18 节装配处留下的空实现让位机制——它们都是为这一刻铺的路，本节把它们真正接上，**`oryxos-core` 一行不改**。

**本节第一次让"Agent 能动手"成为可运行的事实**：工具真正进容器、`oryxos tool list` 看得见、一次对话里模型点名一个工具真的会被执行。这一点与第 19 节（只交付库代码、没有可演示的端到端功能）不同，原因是本节落下了沙箱的**临时装配实现**（见仲裁 1），第 19 节当时卡住的那个"没有可注入的沙箱"的硬约束被解开了。

**本节交付物范围**（课件「本节交付物」逐项 + 已报批的扩展项）：

- **统一抽象**：`OryxTool`、`ToolResult`——骨架期已交付，**本节签名一行不改**（仲裁 2）
- **注册表**：`ToolRegistry`——实现第 17 节在 core 留下的接缝，汇聚三种来源、按 Agent 声明的清单过滤
- **注解管道**：`AnnotatedToolAdapter`——把带注解的 Java 方法包装成统一抽象
- **内置工具**：`FileTools`（文件读 / 文件写 / 列目录）、`ShellTools`（执行命令）、`HttpTools`（HTTP GET / POST）；第 19 节交付的 `NotifyTools` **在此完成注册**
- **扩展内置工具**（课件第六部分）：`edit_file` / `grep` / `glob` 扩进 `FileTools`；`ask_user`（`InteractionTools` + 交互接缝及两档实现）；`web_search`（`WebSearchTools` + 搜索接缝及一档实现）；`web_fetch` 扩进 `HttpTools`（**补强新增**，2026-10-15，见 FR-029）
- **MCP（方式二）**：`McpClientService`（启动连接 + 拉工具清单 + 包装注册 + 失联隔离）、`McpToolAdapter`（协议转发 + 结果包装）
- **装配**：`CliAssemblyConfiguration` 新增 Bean 声明——本节**不再零装配**（仲裁 1），工具、注册表、沙箱临时实现、以及第 19 节挂账的通知相关 Bean 全部在此落地
- **沙箱**：`Sandbox` 前向接口"五件"的**第五件**——临时装配实现（前四件骨架期已交付，本节不改）
- **配置**：`.oryxos/mcp_servers.yaml`（第 18 节已建模板，**本节首次真正消费它**，模板结构不改）；Agent 声明工具清单的过滤

### 明确不做（边界）

核心阶段不碰以下各项，本节一律不做：

- **Tool Policy**（哪个 Agent 能用哪些工具的完整 allow/deny 规则）——核心阶段先用「白名单 + Agent 声明的工具清单」顶住；
- **工具太多时的按需加载**（工具检索 / 懒加载 / 分组暴露）；
- **把 OryxOS 自己变成 MCP server 对外暴露**；
- **完整的容器级沙箱**（namespace / cgroups / seccomp / microVM）——归扩展阶段；
- **一次响应里多个工具并行调**——同步执行模型；
- **沙箱白名单的实现本体**（`WhitelistSandbox`）——归第 23/24 节，本节只以接口调用形式接入 + 挂临时实现（仲裁 1）；
- **Memory 的两个内置工具**（`save_memory` / `recall_memory`）——归第 22 节（仲裁 9）；
- **Skill 绑定**（方式一里的 `skills/` 软连接与 Skill 元数据注入）——归第 29 节（仲裁 8）；方式一在本节只到「配置里声明 MCP server」这一步；
- **MCP server 的进程生命周期治理**（重启、健康检查、重连退避）——本节只做「连不上就 WARN 跳过」；
- **MCP 的认证 / OAuth 授权流程**——本节只支持配置里给出的启动命令与环境变量；
- **Web Service 侧的 `/api/v1/tools` 端点**——归第 26 节（本节只保证 `oryxos tool list` 命令能看到工具）；
- **定时触发**（第 25 / 28 节）与**交付 Demo 的完整跑通**（第 31 节）。

## 冲突仲裁记录（本规约据此撰写，后续 plan / tasks 不得偏离）

1. **【已报批，2026-10-14 用户裁决】装配解冻：本节首次把工具装进容器，沙箱挂临时实现**——这是对**第 19 节裁决 4**（「本节零装配…… `NotifyTools` 的 Bean 声明一并归第 24 节…… MUST NOT 造「全放行」的占位沙箱」）的**有意推翻**。理由三条：① 第 19 节不装配的**根因**是「没有可注入的沙箱 Bean」，而课件「本节交付物」明写 `Sandbox` 前向接口五件**含临时装配实现**——根因在本节被解开；② 课件同时明写「`NotifyTools`（19 节）**在此完成注册**」——不装配就无从完成注册；③ 不装配则本节交付的「Agent 真能调工具」无从演示，与章程原则 15「每个 user story 完成后有可演示 Demo」冲突。落地：`oryxos-tool` 的 sandbox 包新增临时实现，在装配处声明为沙箱 Bean，**并与既有的让位机制一致**——第 24 节落地真实现后**自动让位，不需要回头删代码**。**连带影响如实记录**：第 19 节挂账的 `RestClient` / `WebhookNotifyAdapter` / 渠道注册表实现 / `NotifyTools` 的 Bean 声明一并**从第 24 节提前到本节**。**残余风险如实记录**：临时实现让白名单校验在第 20~23 节之间处于「不生效」状态，即**本节交付的运行时没有 Tool 治理**。缓解四条：① 类名与 javadoc 明示「临时装配、第 24 节必须替换」；② 装配时打一条 WARN 日志；③ 第 24 节用同类型 Bean 自动覆盖；④ `CLAUDE.md` 与本节验收报告均记明该窗口期。**第 24 节课件的交付物清单里没有这个临时类**（已核对：只有 `Sandbox` 四件 + `WhitelistSandbox` + 三个配置属性类），印证了「临时」的定性。

2. **【已报批，2026-10-14 用户裁决】`OryxTool` 保留骨架期的 String 口径，不改成课件示意的签名**——课件 §三写 `JsonSchema getInputSchema()` / `ToolResult execute(JsonNode input)`，而骨架期交付的契约是 `String getInputSchema()` / `ToolResult execute(String inputJson)`（其 javadoc 已写明「JSON 以字符串承载，避免给 core 引入额外依赖」，是**有意为之**）。裁决：**保留 String 口径**。理由：① 改签名属软门禁 ④（修改前序节交付的公共接口），且该口径的设计意图（core 不引额外依赖）今天依然成立；② String 口径与 JSON Schema 文本的语义完全等价，只是承载形式不同；③ 转换成本被**收在一个地方**——注解管道内部做「注解方法的参数对象 ↔ JSON 字符串」的互转，工具实现与调用方都不感知。**课件的签名形式记为已知偏差**，进验收报告。

3. **【已报批，2026-10-14 用户裁决】显式声明 MCP Java SDK 依赖，并按真实 API 落地**——课件用的是示意 API（`McpClient.connect(cfg)` / `client.callTool(name, input)`），与真实 SDK 的形状不同。已实测：目标坐标**在本地仓库里存在**，但**不在本项目的依赖树上**、**也不由任何 BOM 托管**——故必须**显式声明并写死版本号**。裁决：按**真实 API** 落地，课件的示意调用记为已知偏差；**统一抽象的公开契约不受影响**——外部 SDK 的形状差异全部被适配器挡在内部，这正是本节立统一抽象的价值所在。**副作用如实记录**：响应式基础库已在 classpath 上（自第 16 节经模型依赖传递引入），本节**不新增响应式依赖边**；章程原则 8「不引入响应式编程」的判定口径是**本项目源码**（H4 不变量 ⑤ 的扫描只覆盖本仓源码），第三方库内部实现不构成违反。

   **【追加裁决，2026-10-14 —— 单加 `mcp-core` 不可用，改为一并加 mapper 模块】**：写 plan 前用 `javap` 核实 SDK 字节码，发现**只声明 `mcp-core` 会让启动直接失败**，三条实测证据：① `mcp-core` 里**没有任何** mapper 实现、也没有 ServiceLoader 注册文件（实现类在 `mcp-json-jackson2`）；② 传输层构造器的**唯一**重载要求传入 mapper；③ 不显式给校验器时，客户端构建**主动去 ServiceLoader 找**，而该解析在找不到时**抛 `ServiceConfigurationError`**（不是降级）。故软门禁 ⑤/⑥ 命中，已停下报批。**用户裁决：一并声明 mapper 模块**。落地：`mcp-core` + `mcp-json-jackson2`（同版本号，均由本节显式声明，不由 BOM 托管）。**连带影响如实记录**：发行物新增**五个**工件——`mcp-core`、`mcp-json-jackson2`、`json-schema-validator`、`itu`、`jackson-dataformat-yaml`；已逐一核实**全部已在本地仓库**（注意 `itu` 的 groupId 是 `com.ethlo.time` 而非 `com.networknt`），**离线构建不受影响**。被否方案：只加 `mcp-core` 并自实现 mapper 与校验器（发行物只新增一个工件，但要自持 SDK 的 JSON 契约、接缝更多），未采纳。

4. **`Sandbox` 前向接口"五件"里，前四件骨架期已交付，本节只补第五件**——`Sandbox` / `SandboxAction` / `ActionType` / `SandboxViolationException` 骨架期已在 `oryxos-tool` 的 sandbox 包交付，接口签名**逐字照**技术方案 §6.7（「接口签名里不出现白名单/容器镜像/VM 配置这类某一档实现特有的词」）。本节**不改这四件一行**；课件说的第五件就是仲裁 1 的临时装配实现。课件「实现本体 24 节」指 `WhitelistSandbox`——**本节不实现它**。

5. **注册表实现 core 的既有接缝，core 侧零改动**——课件的 `ToolRegistry` 是一个独立类；本项目第 17 节已在 core 留下「按名查工具 / 列可用工具」接缝，其 javadoc 明写「实现方：`oryxos-tool` 的 `ToolRegistry`（第 20 节）」，且装配处已用**让位机制**声明了空实现占位。裁决：注册表**实现该接缝**，本节把空实现让位掉；`oryxos-core` **一行不改**。课件「按 Profile 的 `tools` 字段过滤」对应接缝的「列可用工具」方法。注册表自身的公开 API（注册工具 / 注册注解 Bean / 判断是否已注册某工具）按**课件给的名字**取（课件 §三与 harness 分别用到「注册」「注册注解 Bean」「判断包含」三个动作）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent 第一次真的动手：工具进了容器、按 Agent 声明过滤、一次调用走完整链路 (Priority: P1)

业务方想让 Agent 会查天气。他在工程里写了一个带注解的 Java 方法（方式三），什么装配代码都不用加。启动后 `oryxos tool list` 里能看到这个工具，名字、用途说明、入参说明三样齐全。开一个对话，问一句需要用到这个工具的问题，模型点名要调它——OryxOS 真的把方法执行了，把结果递回给模型，模型据此给出最终答复。事后去数据库里看，这次工具调用在审计表里留了一条记录。

**Why this priority**: 这是本节的地基，也是"Agent 能动手"这件事本身。没有注册表与注解管道，后面所有工具都无处安放；没有装配，前 19 节交付的一切都还是"实验室里的库代码"。它同时把第 17 节的工具执行器与审计表真正跑活。

**Independent Test**: 纯单测可判定——构造一个带注解方法的测试类，走「扫描 → 包装 → 注册」，断言注册表里能按名查到它，且它作为一个统一抽象实例，名字 / 用途说明 / 入参说明三项都非空；再按一份声明了工具清单的 Agent 配置取可用子集，断言子集**恰好等于**声明清单里已注册的那些。装配是否真的成立由 `oryxos tool list` 实跑判定（人工项）。

**Acceptance Scenarios**:

1. **Given** 一个带注解的 Java 方法，**When** 启动扫描并注册，**Then** 注册表里能按名精确查到它，且它对外表现为统一抽象实例（名字 / 用途说明 / 入参说明齐全）。
2. **Given** 注册表里已有若干工具，**When** 一个 Agent 声明了其中一部分，**Then** 取到的可用子集**恰好等于**声明的已注册工具集合——多出一个（没过滤干净）和少一个（过滤过头）都算错。
3. **Given** 模型点名了一个**不存在**的工具，**When** 执行链路处理这次调用，**Then** 得到一条**失败结果**且落一条失败审计，**循环不被异常打断**。
4. **Given** 三个来源（内置 / 注解 Bean / 外部 MCP）的工具都已注册，**When** 遍历注册表里每一个工具做契约检查，**Then** 每一个的名字 / 用途说明 / 入参说明都非空，缺项数为 0。

### User Story 2 - 内置工具真的读得了文件、跑得了命令、发得出请求，越界会被拦 (Priority: P1)

业务方给 Agent 配了"帮我看看项目里那个配置文件"这类任务。Agent 能读文件、写文件、列目录、执行白名单里的命令、发 HTTP 请求。运维在旁边盯着的是另一件事：Agent 不能乱读、乱跑——所有工具在执行前统一过一层校验，越界的调用直接拦下，**真正的 IO 一次都不发生**。

**Why this priority**: 内置工具是 Agent 的"基本手脚"，没有它们 Agent 只能空谈；而"执行前先过校验"是本节唯一的安全落点，必须与工具同生同长——先做功能后补校验，等于把墙拆了再想起来砌。

**Independent Test**: 每个内置工具各写两条单测——「正常路径能跑通」与「越界会被拦下」，两条都过才算这个工具做完。另有一条顺序断言：校验必须发生在真正的 IO 之前（用调用顺序钉死），校验不过时一次 IO 都不发生。全部不碰外网，秒级跑完。

**Acceptance Scenarios**:

1. **Given** 一个在允许范围内的文件路径 / 命令 / 域名，**When** 调用对应内置工具，**Then** 正常返回结果，成功标识为真。
2. **Given** 一个越界的目标（白名单外的路径 / 命令 / 域名），**When** 调用对应内置工具，**Then** 被拦下、返回失败，且**真正的 IO 一次都没发生**。
3. **Given** 任何一次内置工具调用，**When** 执行，**Then** 校验调用发生在 IO 之前（顺序由测试钉死，不可颠倒）。
4. **Given** 命令工具被调用，**When** 传入的参数里含 Shell 元字符，**Then** 参数**原样直传**、不被 Shell 解释。

### User Story 3 - 不写一行 Java 也能接工具：声明一个 MCP server 就能用，它挂了不拖垮启动 (Priority: P1)

业务方想让 Agent 会查 GitHub PR。社区已经有一个现成的 MCP server，他只需在配置里声明一条（名字、传输方式、启动命令、环境变量），**一行 Java 代码都不写**。OryxOS 启动时自动连上它、把它暴露的工具全部纳入可用集合。第二天那个 server 挂了，业务方发现 OryxOS 照常起得来、其他工具照常能用，日志里只有一条警告。

**Why this priority**: 这是课件主推的接入方式（方式一/二），也是"统一底座"价值的直接体现——业务方只描述"要什么能力"，不写集成代码。失联隔离则是"外部依赖的可用性不是自己的可用性"这条工程底线，缺了它一个第三方 server 就能让整个底座起不来。

**Independent Test**: 纯单测可判定——用一个替身 MCP 客户端：① 它返回的工具清单里的每一项都被包装注册、名字 / 用途说明 / 入参说明来自清单本身；② 调用时参数**原样转发**给 server，返回结果被包成统一结果；③ 让其中一个 server 的连接/列举抛异常，断言：整个过程**不抛异常**、好的 server 的工具**照常注册**、坏的 server 的工具**没有注册**。不碰网络。

**Acceptance Scenarios**:

1. **Given** 配置里声明了 MCP server，**When** 启动连接并拉取工具清单，**Then** 清单里的每一项都被包装成统一抽象并注册进注册表。
2. **Given** 一个已注册的 MCP 工具，**When** 调用它，**Then** 参数被**原样**转发给对应 server，返回结果被包成统一结果返回给调用方。
3. **Given** 配置里声明了多个 MCP server、其中一个连接失败，**When** 启动，**Then** 启动**不抛异常**、其余 server 的工具**全部照常注册**、失败的那个的工具**一个都没注册**，且只留一条警告日志。
4. **Given** 一个 MCP server 长时间不响应，**When** 启动连接它，**Then** 在**有界的等待上限**内失败并 WARN 跳过，**不无限期挂住启动**。

### User Story 4 - 加一个工具的成本恒定在"写一个类" (Priority: P2)

用了一阵子之后，团队发现几个日常高频动作老是缺：改文件里的一段、按正则搜内容、按通配找文件、处理中途向用户提问、上网搜一下。这五样任何一个稍复杂的任务都会用到，属于**基础工具**而不是业务能力，所以底座应该自带。加完之后回头看：安全校验位、审计落库、按 Agent 过滤——这三处**一行都没改**，全都自动生效。

**Why this priority**: 这五个工具本身是"补齐业界水准"，价值明确但不如前三者关键。它真正的价值在于**验证那套抽象**：加工具确实只是"多写一个方法 / 多挂一个实现类"，这正好是对本节设计的一次实战检验。排在 P2 是因为即使只交付前三者，Agent 也已经能干活了。

**Independent Test**: 五个工具各自有单测——改文件的三条（唯一匹配成功 / 找不到报错且文件不变 / 出现多次报错且文件不变）、搜内容与找文件各两条（正常命中 / 超上限截断并注明）+ 一条跳过不可读文件、提问的两条（有交互渠道时能拿到回答 / 无交互渠道时明确报错不卡住）、搜索的两条（正常返回 / 越界域名被拦）。另有一条断言：为这五个工具所做的改动**没有触碰**校验位 / 审计 / 过滤三处的代码。

**Acceptance Scenarios**:

1. **Given** 文件里某段旧文本**唯一出现**，**When** 调用改文件工具，**Then** 替换成功；**Given** 该旧文本找不到或出现多次，**When** 调用，**Then** 明确报错**且文件一个字都不动**。
2. **Given** 一个目录里文件数超过返回上限，**When** 按正则搜内容 / 按通配找文件，**Then** 返回被**截断到上限并注明**，不是无限吐。
3. **Given** 搜索路径下存在二进制或非 UTF-8 文件，**When** 按正则搜内容，**Then** **跳过那个文件**、整次搜索**不中断**，其余文件的命中照常返回。
4. **Given** 一个**没有**人在另一端等着回答的场景（无人值守渠道），**When** 调用提问工具，**Then** 得到明确的"不支持交互"失败结果，**不静默卡住**。
5. **Given** 搜索工具被调用，**When** 目标域名在白名单外，**Then** 被拦下——**不因为它叫"搜索"就绕过**与 HTTP 工具同一层的治理。
6. **Given** 新增了这五个工具，**When** 检查校验位 / 审计落库 / 按 Agent 过滤三处的代码，**Then** 改动行数为 **0**。

---

### Edge Cases

- **模型点了一个不存在的工具名** → 注册表查不到返回空，执行链路转成「失败结果 + 落一条失败审计」，**不抛异常打断循环**（这是接缝的既有契约，本节不得违反）。
- **某个工具漏了入参说明** → 模型侧翻译 Function Calling 格式时拿不到参数说明、直接卡住。契约检查必须在**这里就红**，而不是等到运行期。
- **Agent 声明的工具清单里有一个注册表里没有的名字** → 记一条 WARN 并跳过，**不抛异常**（一个笔误不该让整个 Agent 起不来），但**MUST NOT 静默**——WARN 是可见的。过滤结果恰好等于「声明清单中确实已注册的那些」。
- **两个来源的工具重名**（例如外部 MCP server 暴露了一个与内置工具同名的工具）→ **保留先注册者、记 WARN**。安全侧优先：外部 server 不得借重名劫持底座自带工具。注册顺序确定：内置与注解 Bean 先、MCP 后。
- **`edit_file` 的旧文本找不到 / 出现多次** → 明确报错，**文件一个字都不动**（不允许"改了一半"的中间态）。
- **`grep` 读到二进制 / 非 UTF-8 文件** → 跳过该文件，**不中断整次搜索**；其余文件的命中照常返回。
- **`grep` / `glob` 命中数超过上限** → 截断到上限并**注明已截断**（超大目录一次全吐出来会把模型的上下文撑爆）。
- **`ask_user` 遇到无人值守渠道** → 明确报「不支持交互」；**`ask_user` 读到输入结束（终端关闭）** → 明确报错，不返回空回答冒充"用户什么都没说"。
- **`web_search` 目标域名在白名单外** → 被拦下，与 HTTP 工具同一层治理，一次请求都不发。
- **`web_search` 搜索引擎返回空结果** → 返回一条明确的"未找到结果"，**不算失败**（搜不到不是故障）。
- **`web_search` 网络不可达** → 返回**可重试**的失败结果（区别于"搜不到"）。
- **MCP server 长时间不响应** → 在有界等待上限内失败并 WARN 跳过，**不无限期挂住启动**（第 25 节的定时任务不能被一次启动连接永久卡住）。
- **配置里一个 MCP server 都没声明**（默认状态）→ 启动正常，注册表里没有 MCP 来源的工具，**这是预期状态**。
- **白名单校验不通过** → 抛校验异常，复用执行链路**既有的失败审计路径**（`success=false` + 错误信息），**不为它新增第二条写入路径**。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供一个**统一的工具抽象**，约定四件事：工具名、用途描述、入参说明（JSON Schema）、执行入口（JSON 入参 → 结果）。不管工具来自内置、注解 Bean 还是外部 MCP server，MUST 全部收敛到这一个抽象；**执行链路 MUST NOT 感知工具来源**。
- **FR-002**: 入参说明 MUST 是**必备项**：任何工具缺了它，模型侧翻译 Function Calling 格式时就拿不到参数说明、直接卡住。系统 MUST 有一条**遍历注册表里每一个工具**的契约检查，断言名字 / 用途说明 / 入参说明三者都非空——**新工具自动纳入检查**，漏实现者立刻红。
- **FR-003**: 执行结果 MUST 携带四样：成功标识、结果内容、错误信息、**是否可重试**（循环拿到失败结果时要判断这错值不值得再调一次）。
- **FR-004**: 系统 MUST 提供**注册表**统一管理所有来源的工具，并实现 core 侧既有的「按名查工具 / 列可用工具」接缝。本节 MUST NOT 修改 core 侧任何类型（既有契约保持不变）。
- **FR-005**: 注册表 MUST 按 Agent 声明的工具清单过滤出可用子集，过滤结果 MUST **恰好等于「声明清单中确实已注册的那些」**：MUST NOT 多出未声明的工具（越权），MUST NOT 漏掉已声明的已注册工具。声明了但未注册的名字 MUST 记 WARN 并跳过，MUST NOT 静默、MUST NOT 抛异常拖垮 Agent 启动。
- **FR-006**: 系统 MUST 在启动时扫描带注解的 Java 方法（内置工具与方式三的 Plugin Tool 走同一条管道），生成入参说明并包装成统一抽象注册进注册表。业务方新增一个工具 MUST **不需要写装配代码**。
- **FR-007**: 系统 MUST 在启动时连接配置里声明的**每一个** MCP server、拉取它暴露的工具清单、把每一项包装成统一抽象注册进注册表（方式二）。MUST NOT 要求业务方写任何 Java 代码。
- **FR-008**: **单个 MCP server 失联 MUST NOT 拖垮自身启动**：连接或拉取失败时 MUST 只记一条 WARN 并跳过它的工具，OryxOS MUST 照常启动，其余 server 的工具 MUST 照常注册。
- **FR-009**: MCP 连接与列举 MUST 有**有界的等待上限**，server 不响应时 MUST 在有限时间内失败并 WARN 跳过，MUST NOT 无限期挂住启动。取值见 Assumptions。
- **FR-010**: 系统 MUST 提供覆盖「读写文件、跑命令、调外部 API、往外推通知」这条最短链路的内置工具：文件读、文件写、列目录、执行命令、HTTP GET、HTTP POST。第 19 节已交付的通知工具 MUST **在本节完成注册**。
- **FR-011**: 系统 MUST 另提供五个日常高频的基础内置工具：**改文件里的一段**、**按正则搜内容**、**按通配找文件路径**、**处理中途向用户提问**、**用搜索引擎检索网页**。判断标准是「基础工具而非业务能力」——任何稍复杂的任务都会用到。
- **FR-012**: 「改文件里的一段」MUST 要求**旧文本唯一匹配**：找不到 MUST 报错，出现多次 MUST 报错；报错时文件 MUST **一个字都不动**（MUST NOT 留下"改了一半"的中间态）。
- **FR-013**: 「按正则搜内容」与「按通配找文件」MUST 有**返回条数上限**，超出时 MUST 截断并**注明已截断**。取值见 Assumptions。
- **FR-014**: 「按正则搜内容」读到**二进制或非 UTF-8 文件**时 MUST 跳过该文件，MUST NOT 中断整次搜索。
- **FR-015**: **所有工具在执行前 MUST 先过安全校验，且必须是执行的第一步**：文件操作查路径白名单、命令查可执行文件白名单、HTTP 请求查域名白名单。校验不通过时 MUST 直接拦下，**真正的 IO 一次都不发生**。
- **FR-016**: 安全校验的**实现本体**归第 23/24 节；本节 MUST 只以**接口调用**的形式接入，并挂一档**临时实现**让工具能进容器。该临时装配 MUST 满足：① 被同类型的真实现**自动替换**，替换时 MUST NOT 需要回头改本节交付的代码或调用方；② 在装配时留下**明确的警告**，让"校验当前不生效"这件事不可被忽略；③ 类名与说明明示其**临时**定性。
- **FR-017**: 「向用户提问」依赖「当前渠道能不能跟人交互」，MUST 抽成一个**可替换的接缝**：工具只负责把问题递出去、把回答带回来；怎么问、能不能问由装配时注入的实现决定。**拿不到回答时 MUST 明确报错，MUST NOT 静默卡住**；无人值守渠道 MUST 明确报「不支持交互」。核心阶段 MUST 至少提供两档实现：能读终端的、明确不支持的。
- **FR-018**: 「用搜索引擎检索网页」的**搜索引擎** MUST 抽成一个**可替换的接缝**：核心阶段挂一档**免 key** 的实现，换别的搜索引擎 MUST 只新增实现类、MUST NOT 改工具与调用方。工具本身只负责把结果渲染成模型好读的文本。
- **FR-019**: 「用搜索引擎检索网页」走网络，MUST 与 HTTP 工具过**同一层域名白名单**，MUST NOT 因为叫「搜索」就绕过治理。
- **FR-020**: 命令工具 MUST 以**参数数组直传**、MUST NOT 经 Shell 解释；MUST 带超时上限。取值见 Assumptions。
- **FR-021**: 工具调用结果 MUST 走**既有**的执行链路审计路径，成功与失败都落库；MUST NOT 为工具或安全校验新增第二条写入路径、MUST NOT 新增审计逻辑。
- **FR-022**: 新增一个工具时，为「安全校验位 / 审计落库 / 按 Agent 过滤」三处所做的代码改动行数 MUST 为 **0**——三者 MUST 对新增工具**自动生效**。
- **FR-023**: 两个来源的工具**重名**时，MUST 保留**先注册者**并记 WARN。注册顺序 MUST 确定：内置与注解 Bean 先、MCP 后。理由：外部 server MUST NOT 借重名劫持底座自带工具。
- **FR-024**: 本节 MUST NOT 修改 `OryxTool` / `ToolResult` / `Sandbox` / `SandboxAction` / `ActionType` / `SandboxViolationException` 的既有签名与行为；MUST NOT 修改 `.oryxos/mcp_servers.yaml` 的模板结构与键名；MUST NOT 修改 `Profile` / `ProfileLoader` / `ProfileContext` 一行。
- **FR-025**: 本节 MUST NOT 实现沙箱白名单本体（第 23/24 节）、MUST NOT 实现 Memory 的两个内置工具（第 22 节）、MUST NOT 实现 Skill 绑定（第 29 节）、MUST NOT 实现 Web Service 的工具查询端点（第 26 节）。
- **FR-026**: 本节 MUST NOT 引入响应式编程、MUST NOT 自建线程池、MUST NOT 引入异步工具调用；执行模型 MUST 是同步阻塞 + 虚拟线程。
- **FR-027**: MCP server 的凭证（环境变量、token）MUST 走环境变量占位，MUST NOT 落明文；MUST NOT 出现在日志、命令输出与报错信息中。
- **FR-028**: 入参说明的生成与「注解方法参数 ↔ JSON」的互转 MUST 收敛在**一个地方**（注解管道内部），MUST NOT 让每个工具实现各自处理 JSON 编解码。

**以下 FR-029~FR-034 为交付后补强（2026-10-15）追加，不修改 FR-001~FR-028 的任何一条**（软门禁 ① / ② 已报批，见验收报告「交付后补强」一节）。背景：FR-010 / FR-011 交付的 12 个工具覆盖面已够，但**单工具的可用深度**不足，四条经实测确认——读大文件撑爆上下文、`mvn` 必然超时、截断后无法翻页、免 key 搜索对长尾查询返回 0 条。

- **FR-029**: 系统 MUST 另提供**抓取网页正文**的内置工具（`web_fetch`）：取一个 URL，把 HTML 转成纯文本交给模型。MUST 满足：① 首行过与 HTTP 工具**同一层**域名白名单；② **每一跳重定向都重新过一遍**白名单（一个白名单内的域名 MUST NOT 靠一个 `Location` 把请求转去任意主机）；③ 只在响应头声明是 HTML 时才去标签，其余类型原样返回；④ 返回正文 MUST 有字符上限，超出时截断并注明原始长度。
- **FR-030**: 文件读工具 MUST 支持**按行分页**（起始行号 + 最多读多少行两个可选参数），且 MUST 有**默认行数上限**：不传分页参数且文件超过上限时，MUST 返回上限内的内容并**注明总行数与下一页的起始行号**。MUST NOT 因为加分页而改变「小文件」的返回结果——上限是给大文件加的天花板，不是给小文件换的实现。越界读取 MUST 返回明确说明而非报错。
- **FR-031**: 命令工具 MUST 支持**调用方指定超时秒数**，且该值 MUST 有**上限**（超过则夹到上限，MUST NOT 无限期等待）；不指定时 MUST 沿用交付时的默认值（改默认值等于让既有 Agent 的时间预算静默变化）。
- **FR-032**: 「按正则搜内容」与「按通配找文件」MUST 支持**翻页**（跳过前 N 条），截断说明里 MUST 给出下一页的起始位置；「按正则搜内容」MUST 支持**每个命中前后各显示 N 行上下文**，上下文行 MUST 与命中行在格式上可区分，且相邻命中的重叠上下文 MUST NOT 重复渲染。
- **FR-033**: 搜索接缝 MUST 提供**第二档带 key 的实现**（真检索 API），与免 key 档并存；装配处 MUST 按**该 key 是否存在**分流，key 缺失时 MUST 回退到免 key 档（「装上就能跑」这条原则 MUST NOT 被破坏）。两档 MUST 都是同一个接缝的实现，`web_search` 工具、校验位与注册表 MUST 零改动（FR-018 的第二次真实验证）。凭证 MUST 走环境变量占位、MUST NOT 出现在日志、异常消息或任何 `toString` 里（FR-027 同款口径）。
- **FR-034**: 免 key 搜索档 MUST 在请求里**显式声明 `User-Agent`**，MUST NOT 依赖 HTTP 客户端的默认值——该端点按 UA 分流，JDK 默认 UA 被回 HTTP 403（2026-10-15 实测），不声明等于这一档对所有部署环境都不可用。该行为 MUST 有测试钉死（UA 非空且不是客户端默认值）。

### Key Entities

- **工具（统一抽象）**：工具名、用途描述、入参说明、执行入口。三种来源同形——这是本节的基石。
- **执行结果**：成功标识、结果内容、错误信息、是否可重试。
- **工具注册表**：三种来源工具的汇聚点；支持按名精确命中、按 Agent 声明的清单过滤出可用子集、判断某工具是否已注册。
- **内置工具**：文件组（读 / 写 / 列目录 / 改一段 / 按正则搜 / 按通配找）、命令组（执行命令）、HTTP 组（GET / POST / 抓网页正文）、通知组（第 19 节交付）、搜索组（检索网页）、交互组（向用户提问）。
- **MCP server 配置**：配置里的一条声明——名字、传输方式、启动命令、环境变量（外加远程传输时的地址）。第 18 节已交付模板结构，本节只读不改。
- **交互接缝**：把问题递出去、把回答带回来；按渠道挂实现（能读终端的 / 明确不支持的）。
