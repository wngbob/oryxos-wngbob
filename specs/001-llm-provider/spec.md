## 范围说明

本规约覆盖核心阶段 US-1（对接 LLM）的**第一节切片**：Provider 抽象层、Profile 的派生与加载、LLM 调用的审计留痕。上游是 `specs/000-runtime-kernel` 已落地的契约与审计地基（`OryxTool` 契约、`llm_calls` 表骨架）；下游消费者是第 17 节的 ReAct 循环。

**冲突仲裁记录（本规约据此撰写，后续 plan / tasks 不得偏离）**：课件称 Profile 来自 `.oryxos/profiles/` 下独立 YAML、且字段含 `skills` 与 `notify_channels`；这与技术方案 §8.2（`AgentLoader` 扫 `.oryxos/agents/`、由 `AGENT.md` frontmatter 派生 Profile）及章程原则 IV（Skill 绑定的唯一真相源是软连接，不进 frontmatter）冲突。按 `CLAUDE.md`「文档间冲突时，以最新技术方案为准」裁决为：**Profile 由 Agent 目录的 `AGENT.md` frontmatter 派生，字段不含 `skills`、不含 `notify_channels`**。

## Clarifications

### Session 2026-10-13

- Q: Provider 抽象层自身的性能目标如何量化? → A: 转发开销 ≤ 50ms（不含模型推理与网络往返），且不随并存厂商数量增长；沿用上游 `specs/000-runtime-kernel` SC-005 的口径。
- Q: 除数据库审计外，每次 LLM 调用是否还需输出结构化日志? → A: 需要——成功与失败都输出一条结构化 JSON 日志，禁用标准输出，脱敏规则与审计落库同一套；沿用上游 `specs/000-runtime-kernel` FR-074 的口径。
- Q: 实例厂商清单中出现同名重复声明时如何处理? → A: 视为配置错误，启动即报错、不静默取其一（由 FR-005「显式映射不得有歧义」推导）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多 Provider 并存，按名路由不串台 (Priority: P1)

同一个 OryxOS 实例上同时接入多家大模型厂商：运维 Agent 的 Profile 点名用 deepseek，客服 Agent 的 Profile 点名用另一家。两边并存、互不干扰——每次调用必须精确落到该 Profile 点名的那一家；Profile 点名了一个实例上并不存在的厂商时，必须当场给出说得清问题的报错，而不是悄悄换一家或留空跑过去。

**Why this priority**: 这是 Provider 存在的全部理由——上层不感知厂商差异、换厂商不改代码。没有这条，后面的工具翻译与审计都无处附着。

**Independent Test**: 用两个可控的模型替身（stub）分别冒充两家厂商，让一个 Profile 点名其中一家发起调用，验证只有被点名的那家被调用一次、另一家零调用；再让 Profile 点名一个未声明的名字，验证抛出指明该名字的错误。

**Acceptance Scenarios**:

1. **Given** 实例已声明两家厂商、两个 Agent 的 Profile 各点名其一，**When** 分别发起调用，**Then** 每次调用只落到该 Profile 点名的那家厂商，另一家零调用。
2. **Given** Profile 点名了一个实例未声明的厂商名，**When** 加载配置或发起调用，**Then** 系统给出含该名字的清晰错误，不静默改用其他厂商、不留空继续执行。

---

### User Story 2 - 工具说明只翻译、不执行 (Priority: P1)

一次 LLM 调用可以顺带告诉模型"你手上有哪些工具可用、每个工具要什么参数"（即工具说明 / schema）。模型可能回一句"我想调 `http_get`，参数是这些"——注意模型只是**说它想调**。本模块把工具说明翻译成模型看得懂的格式，然后把模型的请求原样交回上层；真正去执行工具的是上层。框架自带的"自动帮忙执行工具"能力必须关闭，否则工具会被执行两次，且绕过了上层统一的执行与审计路径。

**Why this priority**: 这是全项目最易写错、后果最重的一条（章程原则 III 点名的头号风险）。它与 US-1 同为"能稳定调通一次"的最小闭环，必须与路由一起落地，且要有能钉死它的回归测试。

**Independent Test**: 构造一次携带工具说明的调用，捕获实际发给模型的请求，验证其中工具说明已按目标格式生成且非空；同时验证请求上"自动执行"开关处于关闭状态。

**Acceptance Scenarios**:

1. **Given** 一次携带 N 个工具说明的调用，**When** 请求发往模型，**Then** 请求中带有翻译后的工具说明，字段与来源工具一一对齐，且不含任何执行逻辑。
2. **Given** 模型在响应中表达了"想调某个工具"，**When** 调用返回，**Then** 该请求原样交回上层，本模块一次都没有执行该工具。
3. **Given** 一次携带工具说明的调用，**When** 检查发往模型的请求，**Then** "自动执行工具"开关为关闭——任何把它改回开启的改动都必须让对应回归测试立刻变红。

### User Story 3 - Profile 由 Agent 目录派生，配置驱动换模型 (Priority: P2)

业务方在 Agent 目录的 `AGENT.md` 里写清这个 Agent 用哪家厂商、哪个模型、什么温度。想换模型时只改这几行，不碰任何代码。系统启动时把所有 Agent 的 Profile 装载进内存索引供按名查找；某个 Agent 的文件坏了，记错误日志但不拖垮整个实例的启动。

**Why this priority**: 这是"换模型只改配置"的兑现方式，也是后续每节取用 Profile 字段的基础。它不阻塞 US-1/US-2 的调用闭环，故排在 P2。

**Independent Test**: 准备若干合法的 Agent 目录与一个坏文件，启动加载，验证合法 Profile 全字段解析正确、按名可查、坏文件只记错误且其余照常装载；再验证配置里引用的厂商名若不在实例清单中会被判为不合法。

**Acceptance Scenarios**:

1. **Given** 一个字段齐全的 Agent 目录，**When** 加载 Profile，**Then** 身份、厂商（名字/模型/温度）、工具、MCP、渠道、定时、Bootstrap、运行参数等字段全部解析到位，可按 Agent 名查到。
2. **Given** 某个 Agent 的配置文件损坏或字段非法，**When** 启动加载，**Then** 该条记错误日志并跳过，其余 Agent 的 Profile 全部照常装载，实例不中断启动。
3. **Given** 某 Profile 点名的厂商不在实例声明的清单中，**When** 加载校验，**Then** 该 Profile 被判为不合法并给出指明厂商名的错误。

---

### User Story 4 - 每次调用可审计：成败都留痕 (Priority: P2)

审计员事后能查到：某次会话调了哪家模型、输入输出各多少 token、耗时多久；某次调用失败了，失败原因是什么。因此**不论成功还是失败**，每次调用都必须落一条审计记录，按会话关联。只记成功不记失败，等于一次真实事故在系统里完全没留痕迹。

**Why this priority**: 「可审计」是 OryxOS 的差异化卖点，章程原则 VI 要求审计 Day One 落库。它与调用闭环同属本期交付，但因为不阻塞调用本身，排在路由与工具翻译之后。

**Independent Test**: 造一次成功的调用与一次抛异常的调用，验证两次都产生审计记录；失败那条的失败标识为假且带上了原因。再用手工建表脚本建出的库验证这些列真实存在、能存能读。

**Acceptance Scenarios**:

1. **Given** 一次成功的调用，**When** 调用返回，**Then** 落一条审计记录，含厂商、模型、token 用量、耗时、成功标识为真、无失败原因。
2. **Given** 一次失败的调用（超时 / 限流 / 模型报错），**When** 调用抛出异常，**Then** 先落一条成功标识为假、带失败原因的审计记录，再把异常继续上抛给上层处理。
3. **Given** 由手工建表脚本创建的审计表，**When** 写入并读回一条记录，**Then** 成功标识与失败原因两列真实存在、读写一致。

---

### Edge Cases

- Profile 点名的厂商名大小写或前后空格不一致时，视为不同名字（不静默容错），报错须回显原始输入。
- 实例声明的厂商清单为空时，任何 Profile 都无法通过校验——启动不崩，但每个 Agent 都记错误日志。
- Agent 目录存在但缺少 `AGENT.md` 或 frontmatter 不可解析时，按"坏文件"处理：记错误、跳过该 Agent、不影响其余。
- 厂商清单中声明的凭证环境变量缺失时，在加载期即给出指明缺失变量名的报错，且报错内容不含凭证值本身。
- 调用返回的 token 用量缺失（部分厂商不返回）时，审计记录仍必须落库，用量字段留空而非整条丢弃。
- 工具说明为空（本次调用没有可用工具）时，请求正常发出，不因"没有工具"而报错。
- 一次调用既失败又拿不到任何用量信息时，审计仍落一条"失败 + 原因"的记录。
- 实例厂商清单里出现同名重复声明时，启动即报错并指明重复的名字，不静默取其一（显式映射不得有歧义）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每个 Agent 的模型选择 MUST 由其 Profile 声明，至少包含厂商名、模型名、温度；Profile MUST 由 Agent 目录（`.oryxos/agents/<name>/AGENT.md`）的 frontmatter 派生，MUST NOT 要求业务方另写一份独立的 Profile 配置文件。
- **FR-002**: 系统 MUST 在启动时装载全部 Agent 的 Profile 并建立按 Agent 名的内存索引；单个 Profile 损坏或字段非法 MUST 只记错误日志并跳过，MUST NOT 中断实例启动。
- **FR-003**: 实例级 MUST 显式声明可用的厂商清单及各自的凭证来源（环境变量占位）；Profile 点名的厂商不在该清单中时 MUST 显式报错，MUST NOT 静默改用其他厂商或留空继续。
- **FR-004**: 上层传入会话标识、Profile 与提示内容，系统 MUST 按 Profile 选中对应厂商的模型、发起一次调用、把结果原样返回。
- **FR-005**: 厂商名到具体模型的对应关系 MUST 为显式映射，MUST NOT 通过扫描运行容器中同类型的模型对象来推断（多厂商并存时类型相同，扫描必有歧义）。
- **FR-006**: 请求 MAY 携带本次可用工具的说明；系统 MUST 将其翻译为模型可理解的格式随请求发出。
- **FR-007**: 系统 MUST NOT 执行任何工具。模型表达的工具调用意图 MUST 原样交回上层；框架自带的自动工具执行能力 MUST 处于关闭状态。
- **FR-008**: 每次 LLM 调用 MUST 落一条审计记录（含失败），字段至少覆盖：会话标识、厂商、模型、输入/输出/总 token 用量、耗时、成功标识、失败原因。
- **FR-009**: 调用失败时 MUST 先写入成功标识为假、含失败原因的审计记录，再把异常继续上抛，MUST NOT 吞掉异常。
- **FR-010**: 凭证 MUST 只从环境变量读取；代码、配置文件、日志、报错信息中 MUST NOT 出现明文凭证。
- **FR-011**: 审计表的建表 MUST 走手工维护的建表脚本，MUST NOT 依赖框架的自动建表/自动迁移。
- **FR-012**: 审计记录 MUST 按会话标识关联，支持按会话倒序查询调用历史。
- **FR-013**: 每次 LLM 调用 MUST 同时输出一条结构化 JSON 日志（成功与失败都算），MUST NOT 使用标准输出；日志与审计落库 MUST 适用同一套敏感字段脱敏规则。
- **FR-014**: 实例厂商清单中同一厂商名 MUST 唯一；出现重复声明时 MUST 在启动加载期报错，MUST NOT 静默取其一。

### Key Entities

- **Profile**：一个 Agent 的运行时配置，由该 Agent 目录的 `AGENT.md` frontmatter 派生。关键属性：Agent 名、描述、身份（名称 / 人格提示）、厂商选择（厂商名 / 模型 / 温度）、可用工具子集、引用的 MCP 服务、入站渠道、定时任务、Bootstrap 文件列表、运行参数（最大迭代次数 / 最大历史轮数）。**不含** Skill 绑定（唯一真相源是 Agent 目录内的相对软连接）、**不含**通知渠道（归全局注册表）。
- **Provider 声明**：实例级"本机接了哪些厂商、凭证从哪来"的清单项。关键属性：厂商名、凭证的环境变量名。与 Profile 的关系是一对多——多个 Agent 可共用同一厂商。
- **LLM 调用记录**：一次调用的审计留痕。关键属性：会话标识、厂商、模型、token 用量（输入 / 输出 / 总计）、耗时、成功标识、失败原因、发生时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新增一家厂商只需改配置（实例清单加一条 + Agent 的 Profile 改字段），**零代码改动**即可让某个 Agent 用上它。
- **SC-002**: 审计覆盖率 **100%**——每一次 LLM 调用（成功与失败都算）都产生一条可查记录，无遗漏。
- **SC-003**: 配置类错误（Profile 点名了不存在的厂商、凭证环境变量缺失、frontmatter 不可解析）**100%** 在启动加载期被捕获，报错指明具体是哪个 Agent / 哪个厂商 / 哪个变量，且坏配置**不阻断**其余 Agent 可用。
- **SC-004**: 本模块执行工具的次数为 **0**——模型表达的工具调用意图 100% 原样交回上层。
- **SC-005**: 换模型的操作成本从"改代码 + 重新构建"降到"改 Agent 目录里的一行配置"，且**下一次调用即生效**（无需重启以外的额外步骤）。
- **SC-006**: Provider 抽象层自身的转发开销 **≤ 50ms**（不含模型推理与网络往返），且不随并存厂商数量增长。**本节以结构性断言兑现**（调用路径无额外线程切换与网络跳、厂商映射为 O(1) 查表），不引入基准测试设施——核心阶段建基准属 YAGNI（章程原则 II）。
- **SC-007**: 每次调用在结构化日志中的可见性 **100%**——成功与失败都有一条可检索的结构化日志，与审计落库一一对应。

## Assumptions

- 上游 `specs/000-runtime-kernel` 已落地的契约与审计地基可复用：工具抽象（提供名称、描述、入参 schema 三项）、审计表的实体与访问接口、SQLite 数据源配置。本节在其上生长，不重复造。
- 实例的厂商清单与凭证声明写在应用主配置文件（`application.yaml`）中，凭证值以 `${ENV_VAR}` 占位、运行时从环境变量解析。
- 目标厂商的官方接入依赖在其锁定版本清单中真实可用；经实测，`spring-ai-starter-model-deepseek` 存在于项目锁定的 Spring AI BOM 1.1.8 中，而 Spring AI Alibaba BOM 1.1.2.3 中**不含** dashscope（通义千问）starter——故课件的"qwen"仅作场景示意，本期落地的示例厂商为 deepseek。
- 第 16 节为第一节代码课，无前序节的交付物需要依赖；本模块的直接下游消费者是第 17 节的 ReAct 循环，其接口形态（会话标识 + Profile + 提示内容）本期即按该下游的需要定下。
- 核心阶段不做 fallback / 熔断 / hedge racing：厂商故障时错误直接上抛给上层。
