## 范围说明

本节交付 OryxOS 的第二块核心能力：把「想一步（Reason）、做一步（Act）、看结果（Observe）」串成一个循环，直到模型不再需要调工具、或达到轮数上限。它是 Agent 最关键的一段代码，但本身只做**调度**——不调模型、不执行工具，两者分别委托出去。

本节**不做**能力实现，只做**循环 + 编排 + 上下文组装**；循环依赖的四项外部能力（调模型 / 按名查工具 / 读长期记忆 / 持久化会话）以**抽象**形式引入，具体实现由后续节提供（见「依赖与假设」）。

**冲突仲裁记录（本规约据此撰写，后续 plan / tasks 不得偏离）**：

1. **core 侧跨界接缝**：课件骨架里 `ReActLoop` 直接调 `providerService.chat(...)`、`ToolExecutor` 直接「从工具表里找工具」、`PromptBuilder` 直接读记忆模块。这与章程硬约束「`oryxos-core` 不反向依赖任何能力模块」冲突。裁决：**契约先行**——core 定义 `LlmClient` / `ToolCatalog` / `MemorySource` 三个接口，`oryxos-provider` / `oryxos-tool` / `oryxos-memory` 分别提供实现；core 全程不 import 任何能力模块。（此裁决与 `specs/000-runtime-kernel/plan.md` 的「契约在 core、实现在能力模块」一致，其中 `ToolCatalog` 为该 plan 已定名。）
2. **`Session` 归属**：课件把「`SessionManager` 和 `sessions` 表」列为第 18 节交付物，但本节 harness 的 `AgentServiceTest` 断言「结束后 Session 被持久化」。裁决：本节交付 **core 的内存态 `Session` 领域类型** + `SessionService` 接口（持久化接缝，本节只声明、只调用，测试用替身）；第 18 节交付 `sessions` 表 JPA 实体 + Repository + `SessionService` 实现。`CLAUDE.md` 模块表本就把 `Session` 列在 `oryxos-core`。
3. **core 新增 `spring-ai-model` 依赖**：第 16 节已把 `chat(sessionId, Profile, Prompt)` 钉成字面量（不可改），故 core 必须能构造 `Prompt`、读 `ChatResponse`。这是**依赖类型、不是依赖模块**，不违反依赖方向规则。
4. **持久化接缝的接口名定为 `SessionService`（不是课件里的 `SessionManager`）**：上游 `specs/000-runtime-kernel/tasks.md` 的 T036 / T045 已用 `SessionService` 这个名字，其 T077 更明确写着「统一 `SessionManager`→`SessionService` 命名」。本节点名的公开接口若叫 `SessionManager`，第 18 节实现时必然要再改一次名、牵动本节交付的 `AgentService` 与测试。故本节点名 `SessionService`，与上游方向对齐；课件原文的 `SessionManager` 只作历史措辞保留在本条记录里。此裁决已报批（`/speckit-analyze` 后由用户确认）。

## Clarifications

### Session 2026-10-13

- Q: 本节 core 侧跨界接缝（调模型 / 按名查工具 / 读长期记忆）怎么落地？ → A: 三个都建 core 接口（`LlmClient` / `ToolCatalog` / `MemorySource`），实现分属 provider / tool / memory 三模块。
- Q: 本节的 `Session` 类型怎么落地？ → A: core 内存态 `Session` + 持久化接缝（`SessionService` 接口），第 18 节补 JPA 实体、Repository 与实现。
- Q: 会话历史截断时，「一轮」（`maxHistoryTurns` 默认 20 的单位）指的是什么？ → A: 一次处理 = 一个用户往返；「一轮」= 一条用户消息 + 它引发的全部 assistant / tool 消息（含工具往返）。截断只切在用户消息边界上，不得切出悬空片段。
- Q: 模型在最后一轮（第 10 轮）仍然要求调工具时，这一轮的工具要不要真的执行？ → A: 执行。顺序为「调模型 → 累积响应 → 无工具调用则收尾 → 逐个执行工具」，轮数判断在循环头，故最后一轮的工具照样执行；会话历史以「工具请求 + 工具结果」成对收尾。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 循环跑通：一轮能收尾，多轮能接上 (Priority: P1)

用户问「今天天气怎么样，我该穿什么」。系统把这句话追加进会话，组装本轮要发给模型的内容，调一次模型；模型回「我要调 `http_get`」——系统执行它、把结果回灌进会话、再调一次模型；这次模型不再要工具，直接给出穿搭建议，循环收尾。用户问「你是谁」时，模型第一轮就给了答复，循环一轮即止，不产生任何工具调用。

**Why this priority**: 这是本节存在的全部理由，也是 Demo 一（每日天气）对话版能跑起来的唯一前提。没有它，后面的上下文组装、工具执行、审计都无处附着。同时它自带两条最值钱的边界：**轮数上限兜底**（模型反复要调工具时不挂死）与**每轮累积**（事后可审计、下一轮接得上上一轮）。

**Independent Test**: 用一个可控的模型替身与一个可控的工具执行替身，构造三种情形——①模型第一轮就不要工具；②模型第一轮要工具、第二轮不要；③模型每一轮都要工具（永不收敛）。断言：①只调模型 1 次且返回模型文本；②工具被执行且其结果出现在下一轮发出去的上下文里；③模型恰好被调 10 次（一轮不多）且返回的答复含「达到最大轮数」字样。三种情形结束后，会话里都能按序查到本次全部模型响应与工具结果。

**Acceptance Scenarios**:

1. **Given** 一个模型替身，它在第一轮就返回不含工具调用的响应，**When** 用户发一句话，**Then** 模型恰好被调用 1 次，返回的是模型文本，且该响应被追加进会话。
2. **Given** 一个模型替身，第一轮返回「调 http_get」、第二轮返回最终答复，**When** 用户发一句话，**Then** http_get 被执行一次、其结果出现在第二轮发给模型的内容里，且模型响应与工具结果都按序出现在会话中。
3. **Given** 一个模型替身，它每一轮都返回「调同一个工具」，**When** 用户发一句话，**Then** 模型恰好被调用 10 次（一轮不多）、工具也被执行 10 次，返回的答复含「达到最大轮数」字样。
4. **Given** 一个 Profile 把最大轮数配成 3，**When** 模型每轮都要工具，**Then** 模型恰好被调用 3 次——上限可由 Agent 配置覆盖。

### User Story 2 - 每轮上下文：四段顺序、历史截断、日期锚点 (Priority: P1)

每一轮发给模型的内容由四部分按固定顺序拼成：①system prompt（Agent 的人格/指令 + 启动文件，末尾附当前日期时间）②长期记忆（跨会话的那份，没开就跳过）③会话历史（只留最近 N 轮）④当前可用的工具列表。用户改了 Agent 目录里的正文或启动文件，下一轮组装就立刻生效——不需要重启。

**Why this priority**: 这是「模型能不能看见该看见的东西」的唯一出口，也是坑二（上下文撑爆）的解法。没有它，US-1 的循环发出去的就是一坨没有人格、没有历史、没有工具说明的内容，循环转起来也办不成事。

**Independent Test**: 用临时目录造出启动文件与 Agent 正文，构造一段超过 N 轮的会话历史，断言：①拼出的四部分顺序与来源一一对应；②会话历史只保留最近 N 轮、更早的被丢弃，且 system prompt 与最近 N 轮一定保留；③system prompt 末尾含当前日期时间；④改完文件后**下一次**组装立即读到新内容（无缓存）；⑤Agent 显式引用的文件缺失时报错指明是哪个文件，启动文件缺失时至少留下一条 WARN，不静默跳过。

**Acceptance Scenarios**:

1. **Given** 一段超过 20 轮的会话历史与默认配置，**When** 组装本轮内容，**Then** 只有最近 20 轮进入历史部分，更早的轮次不出现；system prompt 与最近 20 轮一定在。
2. **Given** 任一 Agent 配置，**When** 组装本轮内容，**Then** system prompt 的末尾是当前日期时间。
3. **Given** 一份已被读取过的启动文件，**When** 修改其内容后立刻再组装一次，**Then** 新内容出现在这一次的 system prompt 里（无需重启、无需等待）。
4. **Given** Agent 正文里显式引用了一个不存在的启动文件，**When** 组装本轮内容，**Then** 报错且错误信息指明是哪个文件；若缺失的是非显式引用的启动文件，**Then** 至少记一条 WARN 而非静默跳过。

### User Story 3 - 工具执行只有一条路：成败都留痕 (Priority: P2)

模型说「调 http_get」，系统在**唯一一处**找到那个工具、执行它、把结果包好返回给循环，同时落一条调用记录。工具执行成功记成功；工具执行抛异常，异常不被静默吞掉——失败标识与失败原因照样落进记录，错误信息回灌给模型，让模型有机会换个办法。

**Why this priority**: 「可审计」是 OryxOS 的差异化卖点（章程原则 VI），而「执行权收在一处」是第 16 节关掉框架自动工具执行的**唯一理由**——如果这里出现第二条执行路径，那条回归测试就白写了。它不阻塞 US-1（循环可以用替身验证），故排在 P2。

**Independent Test**: 用可控的工具替身分别制造「成功」与「抛异常」两种情形，各执行一次，断言两次都产生了一条调用记录；成功那条的成功标识为真、失败那条的成功标识为假且失败原因含替身抛出的错误文本；失败情形下，返回给循环的是携带错误信息的失败结果而不是未处理的异常。

**Acceptance Scenarios**:

1. **Given** 一个会成功的工具，**When** 执行一次，**Then** 落一条成功标识为真的记录，返回的结果携带工具产出。
2. **Given** 一个会抛异常的工具，**When** 执行一次，**Then** 落一条成功标识为假、失败原因含该异常文本的记录，返回给循环的是携带该错误信息的失败结果。
3. **Given** 模型一轮里要调三个工具，**When** 执行这一轮，**Then** 三个工具**按顺序**逐个执行（不并行），各自留一条记录。

### User Story 4 - 三种触发源同一个入口：当前 Agent 可见、用完即清 (Priority: P2)

CLI、Web、定时三种触发源最终都汇入同一个处理入口。入口在开始时把「当前是哪个 Agent」放进一个对本次处理可见的位置——工具执行时靠它知道自己属于哪个 Agent（工具的接口签名不带 Agent 配置，不改签名）；处理结束——**哪怕是中途抛异常**——必须把它清掉，免得复用同一线程的下一个请求读到上一个请求的 Agent。

**Why this priority**: 这是三种触发源共用同一条链路（章程原则 XIV）的兑现方式，也是 ThreadLocal 泄漏这类「单请求测试永远不报错、只在并发复用时串号」的最阴险 bug 的防守点。它不阻塞 US-1~3，故排在 P2。

**Independent Test**: 用替身构造一次正常处理与一次抛异常的处理，断言：①处理期间能读到当前 Agent，且读到的就是本次会话所属的那个；②正常结束时它被清掉；③抛异常结束时它**也**被清掉；④处理结束后会话被持久化（经持久化接缝调用一次）。

**Acceptance Scenarios**:

1. **Given** 一次正常处理，**When** 处理进行中，**Then** 能读到当前 Agent 且等于本次会话所属的 Agent。
2. **Given** 一次正常处理，**When** 处理结束，**Then** 当前 Agent 已被清掉。
3. **Given** 一次处理，**When** 处理中途抛异常，**Then** 异常照常上抛，且当前 Agent **同样**已被清掉。
4. **Given** 一次正常处理，**When** 处理结束，**Then** 会话已经过持久化接缝被保存一次。

---

### Edge Cases

- **模型一轮里要调多个工具**：按顺序逐个执行，不并行（并行调用明确不在本节范围）。
- **模型要调一个不存在的工具**：工具查找返回空——本节按「失败结果 + 落审计」处理，不抛未处理异常打断循环（与 US-3 的失败路径同一条路）。
- **工具执行抛异常**：见 US-3——不静默吞、不打断整个循环，失败信息回灌给模型。
- **达到轮数上限时模型仍在要工具**：最后一轮的工具**照常执行**（顺序为「调模型 → 累积 → 判断是否收尾 → 执行工具」，轮数判断在循环头），再强制收尾，返回的答复 MUST 含「达到最大轮数」字样。
- **会话历史恰好等于 N 个用户往返**：不截断（边界值不应误伤）。
- **某一轮的 assistant 消息里同时含工具调用与文本**：该轮的文本与工具调用属于同一条 assistant 消息，不拆成两条。
- **长期记忆未启用**：PromptBuilder 跳过该部分，不报错、不塞占位文本。
- **Profile 引用的启动文件缺失**：显式引用缺失 → 报错并指明文件；非显式引用缺失 → 至少 WARN。
- **会话为空（首次处理）**：会话历史部分只含本轮用户消息。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 一次处理 MUST 按固定顺序推进：把用户消息追加进会话 → 组装本轮要发给模型的内容 → 调用模型一次 → 若模型**没有**提出工具调用，返回其文本作为最终答复并结束；若**有**，执行这些工具、把结果追加进会话、进入下一轮。
- **FR-002**: 循环轮数 MUST 有硬上限，默认 10，可由 Agent 配置覆盖；达到上限 MUST 强制结束并返回含「达到最大轮数」字样的答复，不得无限循环。轮数判断 MUST 在循环头——最后一轮的模型响应照常累积、该轮提出的工具调用**照常执行**，使会话历史以「工具调用请求 + 对应工具结果」成对收尾，MUST NOT 留下悬空的工具请求。
- **FR-003**: 每一轮的模型响应与每一条工具执行结果 MUST 按序追加进会话，使事后可审计、下一轮能接上上一轮。会话消息 MUST 至少能表达：角色（system / user / assistant / tool）、内容、该轮请求的工具调用、工具调用对应的标识、时间戳。
- **FR-004**: 每轮要发给模型的内容 MUST 按固定四部分顺序组装：①system prompt（Agent 人格/指令 + 启动文件，**末尾附当前日期时间**）②长期记忆（未启用则跳过）③会话历史 ④当前可用的工具列表。
- **FR-005**: 会话历史 MUST 只保留最近 N 轮（默认 20，可由 Agent 配置覆盖）；**「一轮」= 一条用户消息 + 它引发的全部 assistant / tool 消息（含工具往返）**，截断 MUST 只切在用户消息边界上，MUST NOT 切出「有工具结果、却无对应工具调用请求」的悬空片段。超出部分丢弃；system prompt 与最近 N 轮 MUST 一定保留。
- **FR-006**: 工具执行 MUST 只发生在唯一一处；每次工具调用不论成败 MUST 落一条审计记录（工具名、入参、结果、成功标识、失败原因、耗时），且与第 16 节的模型调用审计同一口径。
- **FR-007**: 工具执行失败 MUST NOT 被静默吞掉——失败原因 MUST 落进审计记录并回灌给模型；工具执行的异常 MUST NOT 打断整个循环。
- **FR-008**: 三种触发源（CLI / Web / 定时）MUST 汇入同一个处理入口；循环本身 MUST NOT 感知消息来源（不认识 channel 概念）。
- **FR-009**: 一次处理期间「当前是哪个 Agent」MUST 对工具执行可见，且**不修改工具接口签名**。
- **FR-010**: 一次处理结束——**含以异常告终**——MUST 清掉「当前是哪个 Agent」的痕迹；清理由 MUST 发生在异常路径上（finally 语义）。
- **FR-011**: 每次组装内容时 MUST 重新读取启动文件 / Agent 正文 / Skill 绑定，**不得缓存**，改完下一轮即生效。
- **FR-012**: Profile 显式引用的文件缺失 MUST 报错并指明是哪个文件；非显式引用的启动文件缺失 MUST 至少留下一条 WARN。两者 MUST NOT 静默跳过。
- **FR-013**: 本节代码 MUST 只依赖抽象来使用「调模型 / 按名查工具 / 读长期记忆 / 持久化会话」四项外部能力；`oryxos-core` MUST NOT 反向依赖任何能力模块。
- **FR-014**: 调用模型时 MUST 把会话标识一并传出（第 16 节的调用签名要求），使模型调用审计能按会话关联。
- **FR-015**: 本节 MUST NOT 引入响应式编程或自建线程池；执行模型为同步阻塞。

### Key Entities

- **会话（Session）**：一次对话的上下文容器。本次交付**内存态**形态：会话标识、所属 Agent 名、消息列表、创建与最后活跃时间，以及「追加用户消息 / 追加模型响应 / 追加工具结果」三种累积操作。第 18 节补持久化形态（表 `sessions`，字段口径见 `docs/TechnicalSolution.md` §9.2）。
- **会话消息**：会话历史的一条。角色（system / user / assistant / tool）、内容、该轮请求的工具调用、工具调用标识、时间戳。口径与 `specs/000-runtime-kernel/data-model.md` A1 的 `messages_json` 元素结构一致。
- **工具调用审计记录（ToolInvocation）**：每次工具调用的留痕。**骨架期已建**（实体 + Repository + 建表脚本），本节只消费、不新建表、不改列。
- **当前 Agent 上下文（ProfileContext）**：运行态，不落盘。承载「本次处理是哪个 Agent」，入口放置、出口清除。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一句话就能答完的请求，模型恰好被调用 **1** 次、工具被调用 **0** 次。
- **SC-002**: 需要外部数据的请求，工具调用与模型调用交替进行，工具结果**必然**出现在下一轮发给模型的内容里（回灌成功率 100%）。
- **SC-003**: 模型持续要求调工具时，模型调用次数**恰好等于**配置的上限（默认 10，一轮不多），工具执行次数同样等于上限（最后一轮照常执行），返回的答复含「达到最大轮数」字样，且会话历史里悬空的工具请求数为 **0**——死循环发生率 **0**。
- **SC-004**: 一次处理结束后，本次产生的**全部**模型响应与工具结果都能在会话里按序查到（累积完整率 100%）。
- **SC-005**: 单轮发给模型的历史部分，用户往返轮数**不超过**配置的最近 N 轮（默认 20），且该部分**从不**以工具消息开头（悬空片段发生率 0）。
- **SC-006**: 工具调用**无论成败**都留下审计记录（覆盖率 100%）；失败记录带失败原因。
- **SC-007**: 处理以异常告终后，该次处理留下的「当前 Agent」痕迹为 **0**——同一线程的下一个请求读不到上一个请求的 Agent。
- **SC-008**: 修改启动文件或 Agent 正文后，**下一次**组装即读到新内容（生效延迟 = 0 轮，无需重启）。
- **SC-009**: 本节全部自动化测试（5 个测试类）在 `mvn test` 下全绿，且不访问网络。

## Assumptions

- **循环不自建 Agent 抽象**：不用任何框架现成的 Agent / 循环封装，核心循环自实现（章程原则 III；也是课件「为什么自己写」一节的理由）。
- **依赖第 16 节的成果**：按名路由不串台的模型调用、已关闭自动工具执行的请求组装、`llm_calls` 审计写入路径、`Profile` 的 `settings.maxIterations` / `settings.maxHistoryTurns` 两个默认值。
- **`tool_invocations` 骨架期已就位**：实体、Repository、建表脚本与 `success` / `error_message` 两列均已存在，本节只消费。**本节不改表结构、不新建表。**
- **四项外部能力以抽象引入**（见「冲突仲裁记录」1）：`LlmClient`（模型调用，`oryxos-provider` 实现）、`ToolCatalog`（按名查工具，`oryxos-tool` 实现）、`MemorySource`（长期记忆文本，`oryxos-memory` 实现）、`SessionService`（会话持久化，`oryxos-storage` + 第 18 节实现）。**本节只定义与调用，不实现**；测试一律用替身。
- **`Session` 为内存态**（见「冲突仲裁记录」2），持久化由第 18 节补齐；本节对「持久化」的验收以「经接缝被调用一次」为准。
- **`oryxos-core` 新增 `spring-ai-model` 依赖**（见「冲突仲裁记录」3），仅用于构造 `Prompt`、读取 `ChatResponse`；不引入任何能力模块依赖，也不引入新的第三方库。
- **工具失败的重试策略不在本节范围**：课件的「有几样先别做」未列它，`ToolResult` 已预留 `retryable` 标记；本节只保证「失败被记录且不打断循环」。
- **审计入参/结果的敏感字段脱敏不在本节范围**：技术方案、第 17 节课件、章程三处均未提出该要求（它只出现在 `specs/000-runtime-kernel` 的 Clarification Q3，属另一套拆解）。本节按课件的「同一口径」照第 16 节 `llm_calls` 的写法原样落库；若后续节引入统一脱敏单点，再回改本节写入路径。
- **结构化日志**：**每次工具调用（成功与失败各一条）** 按第 16 节既有做法输出结构化日志（SLF4J，禁用 `System.out`），不新增日志框架或日志字段口径。章程附加约束「可观测」要求结构化 JSON 日志覆盖**每一次** Tool 调用——只记失败路径不满足该条；口径与第 16 节 `ProviderService`（成功一条、失败一条）逐字对齐。
- **长期记忆的启用与内容由第 22 节决定**：本节只保证「有就读、没有就跳过、不塞占位文本」。
- **直接下游是第 18 节 CLI**：本节自身没有独立交互入口，端到端证据是「Demo 一（每日天气）对话版能完整走下来」——该 Demo 需要第 18 节的 `oryxos chat` 与第 20 节的 `http_get`，故本节的完成判据以自动化 harness 为准（见 SC-009），端到端 Demo 留作人工项。
- **每个 user story 完成后打 git commit**，同步时机由用户决定（本节流程内不自动 commit / push）。
